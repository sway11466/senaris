# itch の devlog

対象：itch に投稿する devlog の方針と原稿の管理。ページ本体の記入内容は [itch_page.md](itch_page.md)、素材の方針は [marketing.md](marketing.md)。

---

## 方針

itch で能動的に人を呼ぶ口は devlog しかない。ページを置くだけでは流れないため、書く前提で出す（[monetization.md](monetization.md) の itch の性格）。

投稿はプロジェクトページ下部に積まれるほか、フォロワーのフィードと itch 全体の新着一覧に出る。過去の投稿が並ぶこと自体が、後から来た人に動いているプロジェクトだと示す。

ページが Draft のあいだは投稿しない。draft のプロジェクトでも devlog 単体は一覧に出るという報告があり、公式の記述が無いため、出ない前提には立たない。

- 英語で書く。数百語＋画像1〜3枚で足りる。
- 更新は週1。ビルドは当面2週に1回、最低1ステージでもよいので体験版に足す（[monetization.md](monetization.md) の体験版の収録範囲）。章を足す週はリリース告知＋その章の残り要素、間の週は次の更新で入る看板機能を先に語る＝読者には「先週読んだ仕組みが今週遊べる」の繰り返しになる。
- その回のビルドに収録されている要素にしか触れない。遊べないものの話をしない。例外は2つ：次の更新で入る要素を、次回入ると明言して予告する回。製品版（Steam）の予告と明示する回。
- 素材の当ては設計の判断そのもの。陣形スキル（[../gdd/formations.md](../gdd/formations.md)）、マップの型（[../gdd/map_patterns.md](../gdd/map_patterns.md)）、盤の高さと地形（[../gdd/terrain.md](../gdd/terrain.md)）など、なぜそう決めたかが書ける題材を選ぶ。
- itch には投稿を言語ごとに出し分ける仕組みが無い（要確認）ため、日本語版は作らない。読者が英語圏中心で、日本語を足しても届く相手が増えない。

公式サイトにニュース欄やブログを作らない方針（[site.md](site.md)）とは矛盾しない。違いは配信先の有無で、自前サイトのブログは書いても届かず更新義務だけが残るのに対し、devlog は書いた時点でフォロワーのフィードに乗る。

## ネタの型

itch の実例（人気・活発なプロジェクトの devlog）で出現が多かった型。間の週はここから選ぶ。

1. ビルド更新＋パッチノート（最多。本作では章・ステージ追加の回）
2. お披露目系：ユニット・キャラ・敵を1体ずつ紹介。数が多いので枯れにくい。絵は立ち絵の整列ツール（[tools.md](../tech/tools.md)）で組める
3. プラットフォーム進出の告知：Steam ページ公開・ウィッシュリスト開始など。itch に Steam の話を書くのは通例
4. マイルストーン・感謝：公開1ヶ月・DL数・周年
5. ロードマップ／Q&A・FAQ：コメントが溜まってから
6. 小ネタ：制作の裏側・事件記

技術解説（HowTo）も記事単体で人を呼ぶ型だが、数千語・画像数十枚と桁違いに重いので数えない。

## 予定

| # | 内容 | ビルド |
|---|---|---|
| 1 | 出発点（chess problem・乱数なし・生産なし） | 初回（チュートリアル1＋腕試し1本） |
| 2 | 陣形スキル（次週の章の予告） | − |
| 3 | チュートリアル2の残り要素 | チュートリアル2追加 |
| 4 | キャリーオーバー（次週の章の予告） | − |
| 5 | チュートリアル3の残り要素 | チュートリアル3追加 |
| 6 | 未定（Steam ページ公開がこの頃なら告知回） | − |
| 7 | 高難易度ステージの紹介 | 高難易度ステージ追加 |
| 8〜10 | 邪神三部作の要素・キャラ・ストーリー（製品版の予告） | − |

## 原稿の管理

原稿はリポジトリに置く。`channels/itch/devlog/<YYYY-MM-DD>-<スラッグ>.md`。日付は書き始めた日で固定し、公開日は本文冒頭に URL と並べて書く（公開のたびに改名しなくて済む）。記事用に作った画像は `channels/itch/devlog/img/`。

1本のファイルは設計と本文の二部構成にする。

- 設計 … 日本語。狙い（この回で読者に何を持ち帰らせるか）、話の順序、貼る画像の構成。
- 本文 … 英語。公開するものそのまま。

設計は本文の要約ではなく先に決める側なので、本文を直しても設計を追随させない。狙いが変わったときだけ直す。

冒頭の `公開:` 行に URL が入っていれば公開済み、空なら未公開。判定基準はこれ一つに絞る。
