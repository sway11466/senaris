# 開発の進め方（仕様駆動）

doc とコードの関係、変更の順序、ズレの扱いを決める。自動テストの線引きは [testing.md](testing.md)、レイヤー構成は [architecture.md](architecture.md)。

## 位置づけ

仕様駆動開発（spec-driven development）の3段階のうち spec-anchored を採る。

| 段階 | 仕様の扱い |
|---|---|
| spec-first | 仕様を書く → 実装 → 捨てる |
| spec-anchored | 仕様を書く → 実装 → 残してコードと同期し続ける |
| spec-as-source | 人間は仕様だけを編集し、コードは再生成する |

doc/ が仕様、リポジトリのコードが実装。仕様は捨てないが、コード生成の入力にもしない（GDScript は手で書き、doc から生成しない）。

## 仕様の権威

- doc は現時点の正しい仕様。実装はこれに従う。doc とコードが食い違っていると分かったら、どちらかを直す＝放置しない。
- ただし盲目的には従わない。上位の判断基準はゲームが面白いこと（[../concepts.md](../concepts.md) 面白さの核）。仕様どおりに作って面白くないと分かったら、実装を仕様へ寄せるのではなく仕様を変える。
- したがって doc は確定ではないが正本ではある。書いてあるのは「現時点で最も妥当と判断した振る舞い」で、根拠が崩れれば書き換える。各 doc の凡例「決定は覆りうる」と、【確定】の類を書かない方針はこの姿勢の現れ。
- 覆すときは理由を残す（doc 本文の更新＋コミットメッセージ）。設計の背骨に関わる転換は [../adr/](../adr/) に記録する。

## 何が錨か

| 置き場 | 錨 | 内容 |
|---|---|---|
| [../gdd/](../gdd/) | ○ | 盤面の振る舞い（戦闘・移動・占領・AI・UI操作モデル） |
| `tech/`（本ディレクトリ） | ○ | 技術仕様（アーキテクチャ・セーブ・i18n・演出シーン） |
| [../campaign/](../campaign/) | ○ | 各冒険譚の中身（ステージ構成・会話・制作方針） |
| [../art/](../art/) ・ [../audio/](../audio/) | 一部 | 制作方針（絵柄・STYLE 文・調達）は錨でない＝作り方のガイド。命名規約・スロット・autowire のパス規約はコードが依存するので錨 |
| [../concepts.md](../concepts.md) | 上位 | 面白さの判断基準。仕様より上に立つ |
| [../backlog.md](../backlog.md) | × | 未着手の作業の置き場 |
| [../adr/](../adr/) | × | 決定の履歴。現在の姿は各 doc 側が持つ |

- データ正本も錨。CSV（`unit_type.csv`・`terrain_type.csv` ほか）と生成される JSON は仕様と実装の関係にあり、doc と同じ扱い。
- 錨には未実装・未決の章を置かない。doc は現在の姿を書く場所で、これからの話は backlog に置く。doc に「未実装」と書き続けると、doc を読んでも現状が分からなくなる。

## 変更の順序

仕様を先に言える機能（戦闘式・陣形レシピ・占領規則・データ構造）:

1. doc を更新する
2. 実装する
3. テストを足す（[testing.md](testing.md)）

手触りを探る領域（敵AI・カメラ・演出・バランス）:

1. 実装で探る
2. 固まったら doc に固定する

面白さが仕様より上に立つ以上、触ってみるまで妥当な振る舞いが書けない領域を仕様先行に縛らない。testing.md の「触って調整中の領域はテスト後追いでよい／仕様が固まった時点でテストに固定する」と同じ扱い。

どちらの経路でも、振る舞いが変わったコミットに doc の更新を含める。実装だけ先に入れて doc を後日に回すと、その間 doc は嘘になる。

保存されるデータ（セーブ）の構造を変えるときは、版を上げて旧版からの変換を書くところまでを同じ変更に含める。項目を足しただけで旧版もそのまま読める場合でも上げる（[gamesystem.md](gamesystem.md) 版と移行）。

## ドリフト検出

doc とコードのズレは、現状は手動で見つける。機械的に検証する手段はない。

機械的に守られている範囲は自動テストまで＝コード同士の整合と、CSV 正本↔生成物の整合（[test_i18n_translation.gd](../../godot/tests/unit/test_i18n_translation.gd) など）。doc とコードの間には同種の仕組みがない。

専用のツールやスキルは作らない。突き合わせ自体は、疑わしくなったときに対象の doc とコードを指定して AI に都度頼めば足り、たまに見つけて都度正せている現状では作り込みの手間が利を上回る。CI にも組み込まない。単独開発で、面白さを探る試行が頻繁に走る進め方では、マージを止めるゲートは合わない。
